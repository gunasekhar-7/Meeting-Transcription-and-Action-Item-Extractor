# ADR-0006: Explicit LLM orchestration instead of a framework

- **Status:** Accepted
- **Date:** 2026-11-02
- **Stage:** 0

## Context

The intelligence layer makes three structured calls, validates their output, verifies evidence against the transcript, and persists typed rows. Candidate approaches: LangChain (and LangGraph), LlamaIndex, the OpenAI SDK's structured-output helpers plus Pydantic, or a hand-rolled adapter.

Requirements that constrain the choice:

- Strict JSON Schema enforcement with Pydantic as the single schema source.
- Deterministic, unit-testable validation and evidence verification, including rejection paths.
- Provider substitutability (OpenAI-compatible endpoints share one wire format).
- Prompt and model versioning recorded per run.
- No framework-level prompt rewriting that changes behaviour between versions.

## Decision

No orchestration framework. Implement:

- `LLMPort` with `complete_json(system, user, json_schema, model, temperature) -> RawCompletion` carrying text, parsed-or-null JSON, token usage, latency and finish reason.
- `OpenAICompatibleProvider` using the official SDK with `response_format={"type":"json_schema","json_schema":{"strict":true,...}}` where supported, degrading to JSON mode plus validation where it is not.
- Pydantic models as the only schema definition; JSON Schema generated by `model_json_schema()`.
- A validation ladder (parse → Pydantic → evidence resolution → quote verification → owner/deadline sanity) implemented as pure functions in `pipelines/intelligence/validators.py`.
- One repair attempt that feeds the validator's exact error back, then a typed failure.

## Consequences

**Positive**

- Every prompt is a reviewable string in the repository, with a version constant.
- Validation is ordinary Python, fully unit-testable with fixtures and property-based tests — the most important tests in the project.
- No hidden retries, token counting, or prompt templating that changes between library releases.
- The adapter is ~150 lines; a reviewer can read all of it.
- Swapping providers is a config change plus a schema-compatibility check.

**Negative**

- Chain/graph composition, tracing UI, and document loaders are not free; if the product grew to multi-step agents, this would need building.
- Some reviewers equate "uses LangChain" with "knows LLM engineering"; the ADR and code must demonstrate the deeper competence instead.
- Provider-specific structured-output differences (Groq requires all fields required; Anthropic uses a different parameter) must be handled explicitly per adapter.

**Mitigations**

- Documented provider capability matrix in the adapter module.
- A schema-compatibility unit test per provider ensures the generated schema satisfies each provider's constraints (all fields required, `additionalProperties:false`, no unsupported keywords).
- ADR states the threshold for revisiting: if the pipeline needs tool-calling agents or multi-hop retrieval, evaluate LangGraph then.

## Alternatives considered

- **LangChain.** Rejected: its abstractions (chains, runnables, output parsers) duplicate what Pydantic and twenty lines of Python already do here, and version churn would alter prompts. The evaluation requirement makes unexplained prompt mutation a liability.
- **LangGraph.** Rejected for v1: the flow is a fixed three-call pipeline, not an agent graph.
- **LlamaIndex.** Rejected: oriented toward retrieval, which is a non-goal in v1.
- **Raw `requests`.** Rejected: the official SDK handles retries, connection pooling and typed usage objects correctly.
